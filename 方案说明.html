现场方案 · 2026-11-05

B 机通过 A 机的 485 接口操控物联网设备

A 机有 RS485，B 机没有，两者同一局域网。目标是让 B 机像插着 485 线一样操作总线上的设备。

结论

用软件网关，不需要买任何硬件。在 A 机跑一个单文件 Python 程序，把串口翻译成网络协议；B 机用标准 Modbus TCP 客户端、浏览器或 HTTP 直接访问。

代码已写好并跑通自测（12 项断言全过），放在 rs485-bridge/ 目录。今天配好波特率就能通。

关键点：B 机看到的是一台标准 Modbus TCP 设备，不是"远程串口"。网关负责把 TCP 的 MBAP 报文翻译成 485 上的 RTU 帧（加 CRC），把响应翻回来（去 CRC）。所以 B 机侧的软件、组态、脚本全部按 Modbus TCP 写，与现场总线无关。

03三个需要你确认的分叉点

① 设备用什么协议
Modbus RTU → 用 --mode modbus，最省事。
私有协议 / 不确定 → 先用 --mode raw 抓一帧看。
这个决定用哪个模式，其余照抄即可。
② A 机能不能长期开着
能 → 软件网关足够。
不能（笔记本要带走）→ 直接买串口服务器，200 多块的 USR-TCP232-410s 就够用。
③ 有多少个客户端
1–2 个 → 软件网关无压力。
多人同时操作、需要权限隔离 → 串口服务器 + 交换机。
④ A 机是什么系统
Windows → 按 README 直接跑。
Linux / 树莓派 → 同一份代码，--port /dev/ttyUSB0，可做成 systemd 服务长期运行。

04性能边界

485 是半双工总线，同一时刻只能有一个事务。网关内部用全局锁把所有请求串行化——这是物理约束，不是实现缺陷。所以要先算清楚够不够用。

30–70 ms / 次事务
9600bps 下，发 8 字节 + 设备响应 + 收 11 字节。计算值
15–30 次 / 秒
理论上限。要更快就提波特率，或一次多读几个寄存器。计算值
环节9600bps 下的量级说明
USB 轮询延迟1–2 ms已用 set_latency_timer(1) 从默认 16ms 压下来
发 8 字节请求≈ 8.3 ms10 bit/字节 ÷ 9600
设备处理 + 响应10–50 ms取决于设备，手册上一般有标注
收 11 字节响应≈ 11.5 ms同上
不要在总线上做高频轮询
用 9600bps 每秒轮询 50 个寄存器，总线会饱和，表现为"越跑越慢、偶发超时"。正确做法是一次 FC03 读连续的 50 个（一帧搞定），而不是发 50 次单寄存器读。

06现场三个必查项

这三个问题占 485 现场故障的九成，且跟软件无关：

  1. A/B 线接反——现象是完全无响应或收到乱码。断电换线，两秒的事。有些厂家把 A 标成 D+、B 标成 D−，甚至有反着标的。
  2. 没接共地——设备电源不同、地电位差大时必须连 GND，否则时好时坏、一长就丢包。
  3. 拓扑与终端电阻——必须手拉手菊花链，不能星形分叉；超过 50 米或波特率高于 38400，最远两端各加 120Ω。

07安全

网关的本质是把一条 485 总线的写权限暴露到网络上。任何能连上端口的人都能读写总线上的所有设备，请按这个前提部署。

默认配置已收紧的项目（每一条都有对应的自动化测试，见 sec_test.py）：

项目默认行为
CORS默认不发送 Access-Control-Allow-Origin，第三方网页无法跨域调用
界面内置控制台走 /panel 同源提供，无需为用界面而放开跨域
Tokenhmac.compare_digest 常量时间比较，避免逐字节试探
请求体上限 64KB，超限直接拒绝
错误响应只回通用描述，内部异常仅写本地日志
启动横幅Token 掩码显示，避免截图带出完整口令

最小暴露的启动方式：

  • --listen 192.168.1.100 —— 只监听内网那块网卡
  • --allow 192.168.1.50 —— 只允许指定 B 机
  • --token 换成你的长口令 —— HTTP 模式加口令

要跨公网访问，走 VPN 或 SSH 隧道，不要把 502 端口直接映射到公网。Modbus 协议本身没有任何认证机制。

已知局限
不做 TLS，HTTP 模式口令与数据在局域网内明文传输，同一广播域可被嗅探；IP 白名单基于源地址判断，不能防御已控制内网的攻击者；无速率限制。需要更强防护请在前面套 Nginx/Caddy 反代或走 VPN。
